## Intent

Связи требований, кода и тестов. Требования описывают наблюдаемый контракт методологии Atomic Spec 2.0.

## Domain Rules

### DR-1. Создание связей

Сначала объявляется требование и запись реестра; одновременно с новым/изменённым обязательным блоком кода или самостоятельным тестом создаются atomic-spec URI и смысловые пояснения. Правка требований актуализирует затронутые связи.

### DR-2. Разрешимость

DR/BR/AC имеют устойчивые ID вне fenced-блоков; каждый AC — отдельный заголовок со следующим Gherkin-блоком. URI ведёт к существующему пункту зарегистрированного атома.

### DR-3. Границы формальной проверки

getcontext, whereused и comments относятся к явно выбранному scope/revision. Formal PASS не доказывает смысл, полноту реализации либо граф satisfies; требуется чтение кода и поведенческие тесты.

### DR-4. Экземпляр

При подключённом проектном Guard используются его штатные команды и зависимости. Ошибка проекта не разрешает подменить его встроенной копией. Встроенный комплект предназначен для проектов без Guard.

## Acceptance Criteria

### AC-1. Ссылка на AC

```gherkin
Scenario: Ссылка на AC
  Given создан атом из бизнес-шаблона и зарегистрирован его ID
  When исходник ссылается на AC-1
  Then Guard разрешает URI к критерию вне Gherkin fence
```

### AC-2. Неверный пункт

```gherkin
Scenario: Неверный пункт
  Given URI ссылается на отсутствующий DR
  When выполняется audit
  Then результат неполный и код завершения ненулевой
```

### AC-3. Существующий Guard

```gherkin
Scenario: Существующий Guard
  Given проект уже подключил Guard
  When агент готовит контекст
  Then используется проектная команда без запуска bundled setup
```
