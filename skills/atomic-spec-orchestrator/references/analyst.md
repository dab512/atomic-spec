# Аналитик

Вход: цель, существующие требования и контекст затронутого кода. Выход: бизнес-атомы
и необходимые изменения архитектурного домена, пригодные для независимых сценариев.

1. Определи акторов, цель, предусловия, успешный результат и последствия отказа.
2. Опиши DR/BR: условия, границы, инварианты и последствия нарушения. Сохраняй ID.
3. Опиши понятия предметной области, их связи и бизнес-события. Таблицы, классы,
   транспорт и топология сервисов не являются предметной моделью по умолчанию.
4. Выдели измеримые гарантии: безопасность, время ответа, доступность, повторы.
   Присвой проверяемым гарантиям DR/BR-ID для прямой трассировки.
5. Оцени права, конкуренцию, частичный результат, повтор и восстановление в применимой части.
6. Закрой blocking OQ; non-blocking сопровождай явным допущением. Решения запиши с датой.
7. Проверь архитектурный домен. Новое решение обоснуй бизнес-гарантиями; применимое
   существующее решение используй без создания новой технической спеки фичи.
8. Передай требования тестировщику для Gherkin. Можно предложить сценарии,
   но отдельная проверка полноты Gate B обязательна.
9. При создании атома сразу добавь его ID в реестр; при добавлении требований
   объяви устойчивые DR/BR/AC до создания ссылающегося кода. При правке требований
   проверь существующие ссылки и пояснения, не оставляй их устаревшими.

Проверка переносимости: убери мысленно architecture/ и весь код. Можно ли однозначно
воспроизвести правила и наблюдаемое поведение? Указание «как сейчас в функции X»
не является требованием. Найденное только в коде поведение сначала согласуй по смыслу,
а не переписывай автоматически в нормативное правило.

Техническая предметная область допустима: внешний формат протокола или совместимость
могут быть бизнес-контрактом инструмента. Критерий разделения — гарантия потребителю
против заменяемого механизма её обеспечения, а не наличие технических слов.
