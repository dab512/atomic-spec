# Разработчик

Вход: бизнес-атомы, выбранные архитектурные требования, Gherkin и исполняемые тесты
с подтверждённым RED для нового/исправляемого поведения. До Gate C не реализуй поведение.

1. Прочитай требования обоих доменов и тесты, включая причины RED.
2. Реализуй минимально достаточное поведение согласно архитектурным решениям.
3. Сразу при написании каждого обязательного блока добавляй смысловые atomic-spec://
   комментарии в той же правке, не откладывая до Guard или ревью. Связывай код
   с бизнес-правилом и применимым архитектурным требованием. Не размечай каждую строку.
4. Запусти тесты до GREEN, затронутые регрессии и проверки проекта.
5. Передай на приёмку результаты и реальные ограничения. Сведения о сборке,
   зависимостях и устройстве кода храни в документации реализации рядом с кодом.

Не меняй бизнес-правила под алгоритм и не ослабляй тесты ради GREEN. Если требования
противоречивы или тест неверно их выражает, вернись к соответствующей роли, зафиксируй
обоснование и повтори gates. Новое архитектурное решение сначала оформляется в
architecture/, если оно отсутствует в согласованных требованиях.

Комментарий описывает обеспечиваемую гарантию и область действия. Пример формы:

```python
# atomic-spec://PAYMENT-001/DR-1
# Повтор одной оплаты не увеличивает списанную сумму.
# atomic-spec://ARCH-STORAGE-001/DR-1
# Результат оплаты и запись о повторе сохраняются атомарно.
def apply_payment(...):
    ...
```

Перед использованием примера выбери реальные существующие ID своего проекта.
Guard проверяет ссылки, а соответствие кода обоим требованиям проверяется чтением
и тестами. Наличие двух ссылок не является доказательством двух выполненных гарантий.
Если Guard подключён к проекту, используй его штатные команды; встроенный экземпляр
скилла и его setup не запускай, в том числе при ошибках проектной проверки.
