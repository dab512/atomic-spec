# Методология 2.0

Atomic Spec объединяет Domain-Driven, Use-Case-Driven, Requirements-Driven подходы
с исполняемыми тестами до реализации. Один атом — один `*.spec.md` с устойчивым ID,
правилами и наблюдаемыми критериями приёмки.

Спецификации должно хватать для воспроизведения бизнес-функционала без чтения
старого кода. История VCS сохраняет причины решений; актуальный контракт должен
оставаться полным и самостоятельно понятным.

## Бизнес и архитектура

Бизнес-домены описывают акторов, результаты, правила, инварианты и гарантии.
Отдельный домен `architecture/` хранит технологии, границы и контракты компонентов,
альтернативы и условия замены. Он входит в единое дерево спецификации.
Отдельный технический дубль каждой фичи не требуется. Карты файлов, история
отладки и протоколы прогонов хранятся рядом с кодом реализации.

В техническом продукте API или протокол может быть внешним бизнес-контрактом.
Разделяйте гарантию потребителю и заменяемый механизм по смыслу.

## Процесс

Контекст → аналитика / Gate A → Gherkin / Gate B → автотесты / Gate C (RED)
→ реализация / Gate D (GREEN) → приёмка.

Роли — ответственность одного агента или человека; делегирование необязательно.
Каждая роль читает нужные требования и изменяет свои артефакты. VCS, review,
согласования, инструменты и объём проверок определяет проект.

## Статус

`draft → review → ready → implemented → deprecated` — единый жизненный цикл атома.
`ready` означает прохождение Gate B и готовность контракта; работающий код этим
не заявляется. `implemented` требует приёмки в указанной области/ревизии реализации.
Это не означает deployment или готовность на всех стеках. Правка контракта
возвращает атом в `review`. Регрессия отменяет соответствующее утверждение о приёмке.

Необязательные записи implementation/verification хранят доказательства с областью
действия, а не альтернативный жизненный цикл. Каталог не определяет статус.
Нужные атомы читаются через явный реестр; полный обход репозитория не требуется.
