# Миграция на 2.0

Это несовместимое обновление методологии. Предыдущий снимок доступен в
[594a44f](https://github.com/dab512/atomic-spec/tree/594a44f0f8c8916faf96a3c13e3247e83b7ae2d3).
Существующий проект мигрирует осознанно: установка скилла не разрешает переписывать
его требования или обходить рабочий процесс.

| Прежняя конвенция | 2.0 |
|---|---|
| Аналитик → Разработчик → Тестировщик; gates A/B/C | Аналитика A → сценарии B → тесты C/RED → реализация D/GREEN → приёмка |
| Tech Spec каждой фичи | Самостоятельный домен архитектуры; заметки реализации рядом с кодом |
| План тестов до/параллельно коду | Исполняемые поведенческие тесты до нового/исправляемого поведения |
| Сценарии Gherkin без обязательных ID | Устойчивые заголовки AC вне fence и явный реестр |
| Три оси статуса и active по каталогу | Один жизненный цикл, доказательства приёмки со своей областью |
| Обязательные spec/feat/test-ветки | VCS проекта; порядок артефактов spec → test → feat/fix |
| Чтение всего дерева | Связанные атомы и разрешённый ограниченный поиск |

При выделении сохраняйте ID и все нормативные правила. Не занимайте существующий
ID другим смыслом; фиксируйте изменённый контракт и совместимость. Разделяйте DMT
по смыслу. История отладки не превращается в требования архитектуры.
Legacy `active` становится `ready`, а `implemented` требует подтверждённой приёмки
в своей области. Прежние implementation/verification сохраняйте как исторические
свидетельства с реальной областью/ревизией; они не подтверждают готовность нового стека.

Встроен закреплённый Git Guard. Git check использует точные SHA; существующий
Git-проект сохраняет свой проектный Git-aware Guard. Минимум Python комплекта —
3.11. Метаданные APM/plugin имеют версию 2.0.2. У независимого Guard собственная
версия/ревизия; он не переименовывается в методологию 2.0.2.
