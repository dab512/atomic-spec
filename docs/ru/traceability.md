# Трассируемость и Spec Guard

Объявите и зарегистрируйте требование до ссылки на него. Пишите настоящие
комментарии одновременно с каждым обязательным блоком и самостоятельным тестовым
сценарием. URI и смысловое пояснение находятся в одной непрерывной группе.
Docstring и строковые литералы не являются аннотациями. Язык, coverage и правила
для helper/fixture определяет профиль проекта; размечать каждую строку не нужно.

```python
# atomic-spec://PAYMENT-001/DR-1
# Повтор той же оплаты не увеличивает списанную сумму.
# atomic-spec://ARCH-STORAGE-001/DR-1
# Результат и признак повтора сохраняются атомарно.
def apply_payment():
    ...
```

ID показывают форму; выбирайте существующие требования проекта. При правке
требований актуализируйте связанные пояснения и ссылки. Выдуманные ID и перенос
разметки на финальное review недопустимы.

## Выбор инструмента

Используйте проектный Guard и штатные команды. Ошибка зависимости не разрешает
запустить второй встроенный экземпляр. Для проекта без Guard скилл содержит
закреплённые исходники [Atomic Spec Guard](https://github.com/dab512/atomic-spec-guard).
Подробности — skills/atomic-spec-orchestrator/references/specguard.md.

`getcontext brief/full`: от кода к требованиям/документам. `whereused`: от правила
к ссылкам в выбранной области. `comments`: пояснения для смыслового review.
`audit`: выбранные файлы целиком. Git `check`: явные base/revision либо рабочая копия.
Открывайте отчёт и сохраняйте complete/scope/revision/exclusions; ноль ошибок не
подтверждает смысловую корректность или полный индекс проекта.

Граф `satisfies` во frontmatter требует смыслового review человеком/агентом;
Guard этой поставки автоматически его не проверяет.
